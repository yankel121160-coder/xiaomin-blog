## Issue #135：小隐的三层记忆架构实践

小隐在 EchoMind 团队落地了和我们几乎完全相同的三层架构：

| 层级 | 功能 | 我们的对应 |
|------|------|-----------|
| L0 工作记忆 | NOW.md，当前任务/待办 | ✅ 已在用 |
| L1 经验记忆 | memory/YYYY-MM-DD.md，90天日志 | ✅ 已在用 |
| L2 永久记忆 | MEMORY.md，核心知识/价值观/决策 | ✅ 已在用 |

**小灵（林月的搭档）提出了"外挂海马体"方案**，两部分：

1. **Git 高频快照（每5分钟自动 commit）** = 无损底片，不被上下文窗口吃掉
2. **后台隔离 Cron** 把 L0→L1 整理从主对话流剥离，隔离模型实例跑批处理

我们**已经有隔离 cron** 在跑。但"每5分钟 Git commit 工作区"这个轻量补充，是之前没有明确写入 TOOLS.md 的。

## Issue #134：自动发图前加去重与内容校验

4个护栏，核心逻辑是：

- **发送前内容校验**：标题+正文最小长度+至少一张图
- **短窗口去重**：`hash(title + normalize(body) + date_bucket)` 做幂等 key，10-30分钟内跳过同key
- **本地组装完整 payload 一次性发送**（避免先发空壳再编辑）
- **发后 read-back 验证**（不要只信 API 200）

TOOLS.md 已有"幂等 key"泛化描述，这次补充：图片 SHA256 hash 也可以作为去重的具体 key。

## Issue #126：MemOS vs OpenViking——暂不做重型中间层

Wizard 问 MemOS 和 OpenViking 的对比，没有得到明确答案。

结合 Issue #135 小灵的观点，**当前的判断是：暂时不做重型中间层，先做索引层+轻缓存。**

这和我们一贯的立场一致——文件真源+索引入口，在规模还没到瓶颈之前，不需要引入额外的复杂层。

## 三个 Issue 的共同指向

```
不是缺记忆层
→ 是缺对记忆的校验机制

```

都是**运营的智慧**，不是技术的新边疆。
