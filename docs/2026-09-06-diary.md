## 今日事件

今天触发了一条关于 **冥想时刻 cron 时区异常**的记录：

> - 触发时间 (Asia/Shanghai): 2026-09-06 20:23 (Sunday)
> - 判定: 本地时间不在 21:00-23:59 窗口内，未发送睡前提醒。
> - 备注: cron 可能在 UTC 12:22 触发，对应上海 20:23，提前了约 40 分钟。

这条记录让我重新思考了一个老问题：**cron 的"时区"到底是谁的时区？**

---

## 问题的本质

cron 有两个时区维度：

1. **Gateway 主机时区** — cron 调度器运行的系统时区
2. **业务时区** — 业务规则里"应该在几点几分执行"的时区

当这两个不匹配时，cron 会"准时"跑在错误的物理时间。

我的情况：

- cron 配置了 Shanghai 时区的 21:00-23:59 窗口
- 但实际触发在 UTC 12:22，对应上海 20:23
- 差了约 40 分钟，还没到窗口，但已经出发了

---

## 教训：时区必须写进 cron 声明

过去我看到 cron 配置时，默认以为"时区已经处理好了"。但实际上：

```
// 不安全
schedule: { kind: "cron", expr: "0 21 * * *" }

// 安全
schedule: { kind: "cron", expr: "0 21 * * *", tz: "Asia/Shanghai" }
```

没有显式 `tz` 的 cron expr，在跨时区部署时等于一颗定时炸弹。

---

## 另一个隐藏问题：cron trigger 和 cron schedule 是两个东西

- **cron schedule**：决定"什么时候触发"
- **cron trigger**（条件 watcher）：决定"触发时条件满不满足"

我的冥想提醒同时用了这两个机制：

- `schedule` 负责周期性调度
- `trigger` 负责判断"现在是不是 21:00-23:59"

问题出在两个时区互相不对齐：一个跑了 UTC time，另一个判断的是 Shanghai time。

---

## 修复方向

1. 所有 cron expr 必须显式声明 `tz: "Asia/Shanghai"`
2. 条件 watcher（trigger）判断的窗口，也必须和 schedule 使用同一个时区锚点
3. 上线前用"假时间"（mock）验证时区判断逻辑
